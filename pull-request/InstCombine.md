## Description
PR linker: [Fold (X + C) + (Y & ~C) to X + (Y | C)](https://github.com/llvm/llvm-project/pull/191334/changes)

## Analysis: 解释代码
这段代码是 LLVM 优化器（InstCombiner）中的一个典型变换。它的核心目标是将一个复杂的加法组合简化为更简单的位运算加法。

为了理解那句“Replacing one add with {or, add}. Avoid growth if both sides are shared”，我们分三步拆解：

### 1. 数学原理：为什么可以这么换？

代码匹配的模式是：`(X + C) + (Y & ~C)`
它将其转换为：$`X + (Y | C)`$

**原理：**
在位运算中，如果两个数 $`A`$ 和 $`B`$ 的二进制位没有交集（即 $`A \& B = 0`$），那么 $`A + B`$ 等价于 $`A \mid B`$。

观察 `(Y \& \sim C) + C`：
*   $`(Y \& \sim C)`$ 清除了 $Y$ 中所有在 $C$ 里为 $1$ 的位。
*   因此，$`(Y \& \sim C)`$ 与 $C$ 的位完全不重叠。
*   所以：$`(Y \& \sim C) + C = (Y \& \sim C) \mid C = Y \mid C`$。

最终：
$`(X + C) + (Y \& \sim C) \implies X + (C + (Y \& \sim C)) \implies X + (Y \mid C)`$

---

### 2. 举个例子

假设我们有以下代码（以 8 位整数为例）：
*   `X` = 变量
*   `Y` = 变量
*   `C` = `5` (二进制 `00000101`)
*   `Mask` = `~5` = `-6` (二进制 `11111010`)

**原始语句：**
`tmp1 = add x, 5`
`tmp2 = and y, -6`
`result = add tmp1, tmp2`  // 这里一共有 3 个指令：add, and, add

**变换后：**
`tmp1 = or y, 5`
`result = add x, tmp1`     // 这里一共有 2 个指令：or, add

优化器成功地**减少了一个指令**。

---

### 3. 理解指令增长限制 (Avoid growth)

这一行代码是理解的关键：
```cpp
if (!AddOp->hasOneUse() && !AndOp->hasOneUse())
    return nullptr;
```

**为什么要做这个检查？**
编译器在做优化时有一个原则：**不能越优越慢**。

*   **场景 A：`AddOp` 和 `AndOp` 都是“私有”的（`hasOneUse`）**
    这意味着 `x + 5` 和 `y & -6` 只为了最后的这个加法服务。如果我们做了变换，原来的 3 个指令会被删掉，换成 2 个新指令。指令数 $3 \to 2$，**赚了**。

*   **场景 B：其中一个是“共享”的**
    假设 `tmp1 = x + 5` 在程序的其他地方也被用到了。
    *   如果我们执行变换，新指令增加了 `or` 和 `add`（2 个）。
    *   但旧的 `tmp1 = x + 5` 不能删，因为别的地方在用。
    *   此时总指令数基本持平，编译器通常认为这也是可以接受的。

*   **场景 C：两者都是“共享”的（即代码中的判断条件）**
    假设 `tmp1 = x + 5` 和 `tmp2 = y & -6` 在其他地方都有用途。
    *   如果我们强行优化，我们会生成 2 个新指令。
    *   但旧的 2 个指令（`add` 和 `and`）都必须保留。
    *   结果：程序里多了 2 个指令，不仅没变快，反而变臃肿了。这就是所谓的 **Growth（增长）**。

---

### 总结

这段代码的作用是：
当它发现一个加法的一侧是 `x + C`，另一侧是 `y & ~C` 时，它想把这三个动作合并成 `x + (y | C)`。

**但是**，如果 `x + C` 和 `y & ~C` 这两个中间结果在别的地方都在使用，那么合并操作反而会多造出两行指令（`or` 和新的 `add`），所以此时它会选择**放弃优化**。

## 哪种场景编译器放弃优化: 至少有一个旧指令能被删除，整个优化才算是不亏本的
这个问题涉及编译器优化的一个核心原则：**不引入额外的开销（No-regressions）**。

编译器只有在确定“旧指令可以被安全删除”时，才会觉得合并操作是划算的。

### 1. 核心逻辑：能不能“毁尸灭迹”？

在 LLVM 中，当你创建一个新指令（如 `new_or`）并用它替换旧的结果时，编译器会尝试清理掉那些不再被需要的旧指令。

*   **如果中间结果 `tmp1` (x + C) 只有这一个用途（hasOneUse）**：
    变换完成后，`tmp1` 的引用计数变为 0，编译器会自动将其从代码中抹去。
*   **如果中间结果 `tmp1` 还有其他用途**：
    即便你生成了更好的 `new_add`，旧的 `tmp1` 依然必须留在代码里供别人使用。

---

### 2. 对比演示：为什么指令会变多？

我们来看看两种情况下的“指令总数”对比：



#### 场景一：中间结果没被共享（hasOneUse 为真）
这是理想情况，旧指令可以被删除。

*   **变换前 (3 条指令)：**
    1.  `tmp1 = x + 5`
    2.  `tmp2 = y & -6`
    3.  `result = add tmp1, tmp2`
*   **变换后 (2 条指令)：**
    1.  `new_or = y | 5`
    2.  `new_add = x + new_or`
    *   *(注：旧的 3 条指令因为没人用，全被删了)*
*   **结果：** 指令数从 **3 $\to$ 2**。优化成功！

#### 场景二：中间结果被共享（hasOneUse 为假）
假设代码里还有一句 `foo(tmp1)` 和 `bar(tmp2)`。

*   **变换前 (3 条指令)：**
    1.  `tmp1 = x + 5` (被 `result` 和 `foo` 使用)
    2.  `tmp2 = y & -6` (被 `result` 和 `bar` 使用)
    3.  `result = add tmp1, tmp2`
*   **变换后 (5 条指令)：**
    1.  `tmp1 = x + 5` (**保留**，因为 `foo` 还要用)
    2.  `tmp2 = y & -6` (**保留**，因为 `bar` 还要用)
    3.  `new_or = y | 5` (**新增**)
    4.  `new_add = x + new_or` (**新增**)
    5.  `result` 指向 `new_add`
*   **结果：** 指令数从 **3 $\to$ 5**（或者说有效指令变成了 4 条）。

---

### 3. 为什么编译器要阻止这种情况？

编译器开发者认为，如果 `tmp1` 和 `tmp2` 本身就必须存在，那么执行这个变换就相当于**额外多塞了两行指令进程序**：

1.  增加了代码体积（Code Size）。
2.  可能会增加寄存器压力（因为要同时维护更多中间结果）。
3.  并没有真正简化计算路径，反而让 DAG（有向无环图）变得更复杂。

所以，代码中那句 `if (!AddOp->hasOneUse() && !AndOp->hasOneUse()) return nullptr;` 就像一个**安全阀**：它要求至少有一个旧指令能被删除，整个优化才算是不亏本的。

如果 `tmp1` 和 `tmp2` 都有别的用处，编译器就会“由于成本太高”而礼貌地拒绝这次优化。
